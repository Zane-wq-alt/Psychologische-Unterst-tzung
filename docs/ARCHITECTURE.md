# Архитектура «Опоры 2.0»

## Переходное состояние
Точка входа остаётся index.html. Старый runtime вынесен в src/legacy/app.js, стили — в src/ui/legacy.css. Runtime пока остаётся одним совместимым классическим скриптом. Это переходный слой, а не завершённая модульная декомпозиция.

## Целевая структура
    index.html / manifest.webmanifest / sw.js
    src/core/       — схема, миграции, валидация
    src/storage/    — local-first адаптер, backup/restore, будущий cloud adapter
    src/features/   — дневник, планирование, поддержка, общение, отчёты
    src/ui/         — тема, компоненты, навигация, доступность
    src/legacy/     — временный runtime до извлечения функций
    tests/          — проверки схемы, миграций и хранения
    docs/           — аудит, решения и инструкции

## Правила
1. core не зависит от DOM, UI, сети или хранилища.
2. storage отвечает за чтение/запись, экспорт и восстановление; без UI.
3. features используют API core/storage и не читают localStorage напрямую.
4. ui отображает состояние и передаёт действия функциям features.
5. Облачный адаптер — отдельный и необязательный; локальный режим работает без него.
6. Генеративного ИИ и интеграций с моделями в архитектуре нет.
7. legacy извлекается по одной функции после появления тестов.

## Порядок декомпозиции
1. Зафиксировать текущий формат данных и тесты чтения/записи.
2. Выделить схему и миграции в core.
3. Вынести local-first хранение и импорт/экспорт в storage.
4. Переносить функции по областям.
5. Перевести UI на явные модули и удалить legacy только после проверки эквивалентности.
6. Спроектировать независимое облако с opt-in отдельно; секреты не помещать в клиент.

## Инварианты
- Исходные данные не перезаписываются до резервного копирования.
- Неизвестные поля сохраняются при миграции.
- Повторная миграция безопасна.
- Сбой синхронизации не блокирует локальную работу.
- Отключение облака не удаляет локальную копию.

## Реализованное локальное хранилище (schema v1)

- Реализация: `src/core/storage.js`; подключается перед legacy runtime.
- Текущий ключ остаётся `localStorage["opora_v2"]`; версия записывается в поле `schemaVersion: 1`.
- Legacy-объект преобразуется в памяти; неизвестные поля и старые записи сохраняются.
- Перед записью результата миграции, импорта или сброса исходная строка сохраняется в отдельном ключе `opora_v2_backup_<timestamp>`; записанная резервная копия проверяется чтением обратно. Если backup не создаётся или не совпадает с исходной строкой, операция отменяется.
- Проверяются типы основных коллекций (`ci`, `ep`, `ev`, `chat`, `notes`), известные вложенные массивы записей и строковые поля. Неизвестные поля остаются без изменений; `null` в известном массиве/объекте не подменяется значением по умолчанию.
- Повреждённый JSON, некорректные записи и будущая неизвестная версия не перезаписываются: приложение переходит в защищённый режим и предлагает скачать исходную строку или импортировать проверенную копию.
- Запись проверяется чтением обратно. При ошибке или несовпадении выполняется rollback исходной строки; `save` не перезаписывает повреждённое существующее состояние. Если `save` сам нормализует схему, он сначала создаёт backup; обычные autosave уже нормализованного состояния не плодят копии.
- Восстановление проверяет backup-конверт и валидность его raw JSON до записи, затем сохраняет исходную строку без переформатирования и предварительно резервирует текущее содержимое.
- Проверки запускаются командой `node --test tests/*.test.cjs`; fixtures находятся в `tests/fixtures/`.
- Ограничение: это локальная защита от случайной потери данных, а не шифрование. Резервные копии в localStorage не защищены отдельным паролем.


## Фактическая декомпозиция runtime — 2026-11-14

Точка входа остаётся классическим `index.html`, но монолитный runtime больше не подключается. Его код разделён на упорядоченные скрипты, которые используют общий глобальный namespace для сохранения совместимости:

- `src/legacy/00-assets-and-helpers.js`, `src/legacy/10-state.js` — временная совместимость и состояние;
- `src/ui/20-navigation.js` — навигация;
- `src/core/30-reference-data.js` — справочники;
- `src/features/40-predictions.js`, `50-views.js`, `60-weekly.js`, `70-actions.js`, `80-audio.js`, `90-breathing.js`, `95-games-and-startup.js` — области поведения и интерфейса.

Порядок загрузки задаётся в `index.html`; все активные файлы входят в precache Service Worker. Старый `src/legacy/app.js` оставлен как короткая заметка о миграции и не загружается.

Это промежуточная декомпозиция, а не завершённый переход на ES modules: скрипты пока разделяют глобальные переменные и функции. Следующий безопасный шаг — извлекать независимые области в модули с явными API после появления тестов на поведение.

## Необязательная синхронизация

`src/storage/cloud-sync.js` задаёт изолированный контракт без конкретного поставщика. По умолчанию он выключен и не выполняет сетевых запросов. Для включения требуются:
- переданный транспорт с методами чтения и условной записи;
- отдельное явное согласие;
- совпадение ревизии перед записью.

Несовпадение ревизий возвращается как конфликт; удалённые данные не перезаписываются молча. Отключение синхронизации не удаляет локальную копию. Удаление удалённой копии — отдельный метод, который должен поддерживаться backend.

Реальный backend пока не настроен. Нельзя считать контракт действующей синхронизацией или показывать пользователю статус «синхронизировано».

## Центр приватности

`src/features/privacy.js` формирует локальный обзор для раздела «Отчёт и данные». Он показывает состояние ИИ, локального хранения и облака, а также только количество записей по категориям — не их содержимое. Действия экспорта, импорта, восстановления и сброса остаются в том же разделе.

Загрузчик Google Fonts удалён; шрифт использует локальный системный fallback. Новые runtime-модули добавлены в precache, версия кэша обновлена до `opora-v14`.

## Дополнение — registry миграций, безопасный bootstrap и PWA

- Schema migration выполняется через явный registry переходов (сейчас 0 → 1); неизвестная будущая версия не понижается автоматически.
- Первый cloud sync может инициализировать пустой remote только после явного consent и через CAS revision 0. Если удалённая копия уже существует, координатор возвращает конфликт или remote-available и не перезаписывает её молча.
- Последняя remote revision хранится в экземпляре координатора; постоянное хранение и пользовательский Auth/consent UI требуют host-интеграции, которой пока нет.
- Service Worker не активирует обновление принудительно: ожидающая версия показывается пользователю и применяется после нажатия «Обновить». Offline fallback на index.html ограничен навигационными запросами.
- В интерфейс добавлены keyboard focus-visible и prefers-reduced-motion.


## Supabase Auth и cloud UI

- supabase-config.js содержит только публичные project URL и anon/publishable key; service-role ключ не допускается.
- Supabase Auth использует email magic link/OTP. Сессия хранится в sessionStorage, refresh token используется только для получения нового access token.
- Центр приватности показывает вход, список категорий, отдельное согласие, ручную синхронизацию, отключение, удаление remote-копии и восстановление remote snapshot с локальным backup.
- При пустой конфигурации auth и sync недоступны, приложение остаётся local-only. Данные не отправляются автоматически.
- Перед реальным использованием необходима проверка redirect allow list, email templates, RLS двумя аккаунтами и CAS conflict в созданном проекте Supabase.


## Граница consent metadata

Cloud consent хранится отдельно от снимка профиля и резервных копий. Revision используется только для CAS-сравнения текущего пользователя и исключается из JSON export/import. Любая замена локального профиля отзывает сохранённое согласие и отключает cloud coordinator; remote snapshot может быть восстановлен только отдельным действием после локального backup.
