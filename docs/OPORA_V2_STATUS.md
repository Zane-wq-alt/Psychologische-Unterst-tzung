## Что изменено

- Runtime больше не загружает монолитный `src/legacy/app.js`; его содержимое разложено по файлам в `src/legacy/`, `src/core/`, `src/ui/` и `src/features/`.
- Порядок подключения модулей явно зафиксирован в `index.html`; новые файлы включены в precache Service Worker.
- Service Worker использует cache version `opora-v23` (на момент первой записи было `opora-v15`); Supabase transport, E2E-модули и стикеры включены в precache.
- Удалён внешний загрузчик Google Fonts: приложение не делает запрос к fonts.googleapis.com ради шрифта.
- Обычное автосохранение теперь возвращает прежнюю строку localStorage при неудачной записи. Автосохранения не создают отдельную резервную копию на каждый ввод.
- Добавлены тесты для rollback обычного сохранения, локального privacy view и контракта синхронизации.
- 2026-11-16 усилены проверки схемы: известные записи и вложенные массивы валидируются; `null` в известных полях не подменяется defaults; backup и результат записи проверяются чтением обратно; восстановление валидирует raw backup до перезаписи; schema-normalization при `save` защищена резервной копией.
- GitHub Actions для коммита [`b30b256`](https://github.com/Zane-wq-alt/Psychologische-Unterst-tzung/commit/b30b25650aae4b0a926e03e498f56523cc89a095) завершился успешно: проверка синтаксиса JS и 27/27 тестов ([run](https://github.com/Zane-wq-alt/Psychologische-Unterst-tzung/actions/runs/43915773058)).

## Облачная синхронизация: границы текущей реализации

Облачная синхронизация по умолчанию выключена. Модуль `src/storage/cloud-sync.js` не содержит провайдера, SDK, адреса сервера или секретов. Он требует переданный транспорт и отдельное явное согласие; при несовпадении ревизий возвращает конфликт и не перезаписывает удалённую копию.

Рекомендация и сравнение Supabase, Firebase и Appwrite записаны в `docs/CLOUD_SYNC_BACKEND.md`. Для завершения реальной синхронизации необходимы создание отдельного backend владельцем, настройка Auth и RLS, проверка доступа двумя тестовыми пользователями, проверка удаления и конфигурация окружения. Эти ресурсы нельзя безопасно создать или угадать из публичного репозитория. До этого момента локальный режим остаётся единственным активным режимом.

## Проверки и ограничения

- Автоматические проверки запускаются GitHub Actions: синтаксис всех JavaScript-файлов и `node --test tests/*.test.cjs`.
- Проверка браузерного интерфейса, Android/iOS, реального PWA offline/upgrade цикла и восстановления на копии пользовательского профиля всё ещё требуется.
- Текущая миграция сохраняет совместимый ключ `opora_v2` и резервирует исходную строку, но ещё не реализует отдельное целевое пространство имён и двухфазное переключение из контракта `OPORA_V2_FOUNDATION.md`; до этого нельзя считать весь этап миграции закрытым.
- Тестовые fixtures не являются пользовательскими данными. Реальный localStorage пользователя не читался и не изменялся.
- Экспорт JSON не зашифрован отдельным паролем.
- Облачный снимок шифруется на устройстве (см. docs/E2E_CLOUD_DESIGN.md); облако пока не настроено и проверено только на тестовых двойниках сервера, без реального Supabase.
- Исторические диалоги остаются локальным архивом; генеративный чат не запускается.

## Безопасность выпуска

Никаких изменений в `main`, merge или release не выполнялось. Не публиковать эту ветку как production до завершения перечисленных ручных проверок и настройки облака (если облако действительно требуется).


## Дополнение — 2026-11-17

- Runtime теперь читает новый ключ `opora_v2_data_v1`; если он отсутствует, исходный `opora_v2` мигрируется копированием.
- Миграция сначала проверяет исходную структуру, создаёт и перечитывает backup, затем записывает и проверяет новый ключ. Исходный `opora_v2` не удаляется и не перезаписывается.
- После успешной записи сохраняется маркер `opora_v2_data_v1_migration_complete` с версией, временем, ключами и количеством записей по коллекциям.
- При сбое backup/записи запуск блокируется, а исходный ключ остаётся нетронутым. Повторный запуск после успешного переноса идемпотентен.
- Добавлены тесты успешного переноса, сохранения исходника, повторного запуска и отказа при ошибке backup.
- Supabase transport и SQL RLS/CAS миграция добавлены отдельно; облако всё ещё не настроено и не включается автоматически.

## Облачная интеграция — пользовательский слой

- Добавлен Supabase Auth по одноразовой ссылке на почту; callback поддерживает стандартный fragment flow и token_hash flow.
- Сессия хранится в sessionStorage текущей вкладки; access token обновляется через refresh token. В код и репозиторий не добавляются реальные project keys.
- Центр приватности показывает форму входа, отдельное согласие с перечнем категорий данных, ручную синхронизацию, отключение, отдельное удаление облачной копии и восстановление remote snapshot только после подтверждения и создания локальной backup-копии.
- Облачная отправка не запускается автоматически. Пока src/storage/supabase-config.js содержит пустые параметры, вход и sync недоступны, приложение работает local-only.
- Реальный backend не развёрнут и не проверен двумя независимыми аккаунтами; это остаётся внешним блокером.


## Дополнительные гарантии облачного согласия и итог CI

- Согласие на облако хранится отдельно от профиля под ключом opora_cloud_consent_v1; оно не переносится в JSON backup и отзывается при импорте, сбросе, восстановлении локального backup, отключении синхронизации, выходе или удалении remote.
- Cloud revision и consent metadata исключены из экспортируемого JSON и очищаются при импорте, чтобы копия одного аккаунта не переносила разрешение/ревизию в другой.
- Поддержаны callback типов email, magiclink и signup. Одноразовые token_hash и access/refresh token из URL удаляются после обработки.
- Последний подтверждённый CI: [44059184434](https://github.com/Zane-wq-alt/Psychologische-Unterst-tzung/actions/runs/44059184434) — 72/72 unit tests, 3/3 Chromium smoke tests, syntax check успешно.
- Фактическая синхронизация с Supabase не подтверждена: публичные настройки пусты, проект не развёрнут. Требуется тест на двух отдельных аккаунтах до использования реальных данных.


## Дополнение — 2026-11-17…18 (защитные шаги и завершение облачного слоя)

Все изменения в ветке `opora-v2-development`, `main` не менялся. GitHub Actions по этим коммитам успешен (синтаксис, модульные и браузерные тесты).

- **Защита от потери данных между вкладками** (`949a9b3`): `OporaStorage.save()` отказывает с `external-change`, если данные изменила другая вкладка; баннер с выбором «Загрузить свежие данные» или «Сохранить версию этой вкладки» (с копией чужой версии).
- **Локальные уведомления об ошибках** (`src/core/errors.js`): журнал только на устройстве, без данных пользователя, без сети; скачивание и очистка в «Отчёт и данные».
- **Выборочное удаление** (`b6aa001`, `src/features/selective-delete.js`): по разделам, с точкой восстановления; отдельный пункт окончательного удаления точек восстановления и копии прежней версии `opora_v2`.
- **Сквозное шифрование облака** (`c9c0757`, `src/storage/e2e-*.js`, `docs/E2E_CLOUD_DESIGN.md`): AES-256-GCM, ключ данных обёрнут парольной фразой (PBKDF2, 600 000 итераций) и ключом восстановления; сервер принимает только формат `opora-e2e` (миграция проверена на локальном Postgres 16 с заглушкой auth).
- **Слияние по записям** (`d99cedb`, `src/storage/merge.js`): трёхстороннее, на устройстве; точка восстановления `before-cloud-merge`; сходимость проверена случайной симуляцией двух устройств.
- **Стикеры вынесены из 500-КБ скрипта** в `assets/stickers/*.webp` (56 файлов), включены в офлайн-кэш (`sw.js`, `opora-v23`).
- **Ограничение числа точек восстановления**: хранятся последние 10 обычных; копии перед миграцией не удаляются (раньше копились без предела и могли исчерпать лимит localStorage).

### Что остаётся (требует внешних действий или отдельного решения)
- Реальный Supabase-проект: создание, Auth, применение двух миграций, проверка RLS двумя аккаунтами, проверка удаления. До этого облако проверено только на двойниках сервера и локальном Postgres.
- Ручной тест на Android/iOS и реальный цикл обновления PWA.
- Переход с classic scripts на изолированные ES-модули (этап 3 выполнен частично).
- Резервные копии по-прежнему в localStorage (лимит браузера ~5 МБ); хранилище IndexedDB для копий не реализовано. Экспорт JSON и точки восстановления не зашифрованы.
- Одновременная правка одной записи на двух устройствах даёт дубликат (потери нет), конфликт листьев решается в пользу устройства, с которого идёт синхронизация.
