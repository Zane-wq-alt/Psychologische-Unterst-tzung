# Сквозное шифрование облака «Опоры»

## Что защищено и от кого
- Провайдер облака (Supabase) и любой, кто получил доступ к базе, видят только непрозрачный блок: размер, время изменения, параметры ключей. Содержимое дневника, профиля и заметок им недоступно.
- Защита от подмены: AES-GCM проверяет целостность; изменённый блок не расшифруется.
- Не защищено: локальные данные в браузере, экспорт JSON и локальные точки восстановления (они открытые). Устройство с уже разблокированным облаком (ключ в памяти страницы). Метаданные: сервер видит, когда и насколько часто меняется копия. Откат к более старой версии блока сервером техническим способом не предотвращается (сервер может вернуть прежний валидный блок).

## Формат (payload в `opora_snapshots`)
```
{ format: "opora-e2e", v: 1, alg: "AES-256-GCM", iv, ct,
  wraps: [ { type: "passphrase", kdf: "PBKDF2-SHA256", iter, salt, iv, wk },
           { type: "recovery",   kdf: "HKDF-SHA256",   salt, iv, wk } ] }
```
- Данные шифруются случайным ключом данных (DEK) на устройстве; на каждую запись новый IV.
- `wk` — DEK, зашифрованный (AES-GCM) ключом из парольной фразы или из ключа восстановления (160 бит). Тип обёртки входит в AAD, обёртки не взаимозаменяемы.
- Смена фразы заменяет только обёртку фразы, данные не перешифровываются; ключ восстановления остаётся прежним. Новая обёртка попадает в облако при следующей синхронизации.
- Фраза не короче 10 символов (NFKC). При чтении параметры KDF проверяются по границам (100 000 – 5 000 000 итераций).
- Схема таблицы не меняется (jsonb). Миграция `202611170002_e2e_only.sql` добавляет ограничение: сервер принимает только формат `opora-e2e` (`NOT VALID`, существующие строки не ломает).

## Потоки
- Первое устройство: фраза (дважды) → создаётся DEK и ключ восстановления → ключ показывается один раз, облако включается только после подтверждения «Я сохранил(а) ключ».
- Следующее устройство: вход в аккаунт → фраза (или ключ восстановления) → проверка на существующей облачной копии.
- Ключ хранится только в памяти страницы. После перезагрузки облако нужно разблокировать заново; выход и «Заблокировать облако» стирают ключ из памяти.
- Нешифрованная копия в облаке не открывается и не перезаписывается автоматически.

## Что дальше (слияние по записям)
Слияние будет выполняться на клиенте после расшифровки, поэтому серверной схемы не потребует. Для него нужны стабильные идентификаторы записей, метки изменения и «надгробия» удаления в локальной модели данных (отдельная миграция схемы). Эти метки войдут в тот же зашифрованный снимок.
