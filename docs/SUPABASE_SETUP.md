# Подключение независимой облачной синхронизации

Сейчас приложение локальное. Добавленный адаптер — рабочий транспортный слой, но не готовый аккаунтный сервис: владелец должен создать собственный проект Supabase, настроить Auth и передавать пользовательский access token. До этого облако не настроено, а данные остаются на устройстве.

## 1. Создать backend

1. Создать проект Supabase в регионе Frankfurt (Central EU), если он доступен в выбранном тарифе.
2. В SQL Editor выполнить миграции по порядку: `supabase/migrations/202611170001_opora_snapshots.sql`, затем `supabase/migrations/202611170002_e2e_only.sql` (сервер перестанет принимать открытые, нешифрованные снимки).
3. В Authentication включить выбранный способ входа и настроить разрешённые redirect URL.
4. Проверить RLS минимум двумя отдельными тестовыми аккаунтами: каждый аккаунт должен видеть только свою строку; попытка чтения/изменения чужого user_id должна возвращать пустой результат или отказ.
5. Проверить push при ожидаемой ревизии, конфликт при устаревшей ревизии и удаление облачной копии.

## 2. Подключить клиент

Создать адаптер:

```js
var transport = OporaSupabaseTransport.create({
  url: "https://YOUR_PROJECT.supabase.co",
  anonKey: "YOUR_PUBLISHABLE_OR_ANON_KEY",
  accessToken: function () {
    return authClient.auth.getSession().then(function (result) {
      return result.data.session && result.data.session.access_token;
    });
  }
});
var cloud = OporaCloudSync.create({ transport: transport });
```

`authClient` здесь — клиент Supabase Auth, созданный приложением-хозяином. В репозитории намеренно нет URL проекта, ключей или пользовательских токенов. Публичный anon/publishable key не заменяет авторизацию. Никогда не использовать service-role key в браузере.

Перед вызовом `cloud.enable(true)` интерфейс обязан отдельно показать, какие категории данных будут отправлены, где они будут храниться, как отключить синхронизацию и удалить облачную копию. Без отдельного согласия не вызывать enable/sync. Локальное сохранение должно продолжать работать при ошибках сети.

## 3. Протокол

- `pull()` читает только строку текущего пользователя благодаря RLS; отсутствие строки означает ревизию 0.
- `push()` вызывает SQL compare-and-swap RPC: новая ревизия создаётся только если ожидаемая ревизия совпала. Конфликт возвращает текущую ревизию и снимок, без молчаливой перезаписи.
- `deleteRemote()` удаляет только строку текущего пользователя.
- В таблице хранится JSONB-объект формата `opora-e2e`: снимок шифруется на устройстве (AES-256-GCM) до отправки. Провайдер видит размер, время изменения и служебные параметры, но не содержимое. Ключ данных хранится в облаке только в обёрнутом виде (под парольной фразой через PBKDF2-SHA256, 600 000 итераций, и под ключом восстановления). Потеря и фразы, и ключа восстановления означает потерю облачной копии; локальные данные это не затрагивает. HTTPS защищает передачу, RLS — доступ на уровне БД. Экспорт JSON и локальные точки восстановления по-прежнему не зашифрованы.

## Ограничения перед включением

Этот репозиторий не может создать Supabase project, включить Auth или подтвердить RLS в чужой инфраструктуре. Пока эти шаги не выполнены и не проверены двумя аккаунтами, облако нельзя показывать как настроенное или включать в production. Не переносить реальные дневники в облако до отдельной оценки условий провайдера, срока хранения, удаления и доступа оператора.


## Первый запуск синхронизации

Координатор синхронизации теперь различает сценарии первого запуска:
- Remote revision 0 и пустой remote: локальный снимок может быть отправлен условной записью с `ifMatch: 0`, но только после согласия.
- Remote уже содержит данные, а локальная ревизия неизвестна: возвращается конфликт с remote snapshot; молчаливой перезаписи нет.
- Локальный и удалённый снимки пусты: запись не создаётся.
- При последующих вызовах вызывающая сторона должна сохранить возвращённую revision в локальном состоянии и передавать её при следующем sync. До появления auth/UI интеграции это остаётся контрактом, а не пользовательским end-to-end потоком.


## Настройка email magic link и клиента

1. В Supabase Authentication включить Email provider и magic link/OTP. В redirect allow list добавить точный адрес приложения, включая путь index.html, если он используется.
2. В src/storage/supabase-config.js заполнить url проекта и публичный anon/publishable key. Эти значения не являются service-role секретом. Никогда не добавлять service_role.
3. Проверить письмо и возврат в приложение: callback принимает стандартный Supabase fragment (access_token, refresh_token, type=magiclink) и token-hash callback. Одноразовые токены удаляются из адресной строки после обработки.
4. В приложении открыть «Отчёт и данные» → облачный блок, запросить ссылку на почту, войти, прочитать перечень отправляемых категорий и поставить отдельную отметку согласия.
5. Нажать «Синхронизировать сейчас» вручную. Автоматической отправки при запуске/сохранении нет.
6. Проверить конфликт на двух тестовых аккаунтах и удостовериться, что RLS не позволяет читать чужую запись. Только после этого можно использовать облако для каких-либо реальных данных.

Пока конфигурация не заполнена, клиент не выполняет auth/network запросы. Сессия живёт только в sessionStorage; закрытие вкладки требует нового входа.


## Согласие и экспорт

Согласие хранится отдельно от пользовательского профиля и не включается в backup. Импорт, локальный сброс, восстановление локального backup, отключение sync, выход и удаление remote отзывают согласие на этом устройстве. Cloud revision и consent не экспортируются и не импортируются вместе с JSON, поэтому перенос файла на другое устройство не переносит авторизацию или разрешение на отправку данных.
