# Облачный backend для «Опоры»: выбор и критерии

Дата оценки: 2026-11-14

## Решение

Рекомендуемый кандидат для первой реализации — **Supabase в регионе Central EU (Frankfurt, eu-central-1)**. Это рекомендация для проверки, а не утверждение, что backend уже создан или соответствует всем требованиям проекта.

Почему этот кандидат:
- PostgreSQL подходит для одной пользовательской записи-снимка и атомарного сравнения ревизий.
- Supabase Auth выдаёт пользовательскую идентичность, а Row Level Security (RLS) позволяет ограничить строки текущим пользователем.
- Для проекта доступен регион Frankfurt. Выбор региона определяет расположение основной базы, Auth и Storage, но сам по себе не доказывает соответствие GDPR и не означает, что любая обработка данных остаётся строго в этом регионе.

## Сравнение кандидатов

| Кандидат | Сильные стороны | Риски и стоимость сопровождения |
|---|---|---|
| Supabase | PostgreSQL, Auth, RLS, EU-регион Frankfurt | Нужно тщательно настроить grants и RLS; выбрать регион недостаточно для юридической оценки потоков данных |
| Firebase / Firestore | Управляемая инфраструктура, правила доступа и региональные настройки | Правила безопасности требуют аккуратного проектирования; пересекающиеся правила могут расширять доступ, поскольку разрешения объединяются логикой OR |
| Appwrite | Регион Frankfurt; облачный вариант и self-hosting | Self-hosting означает самостоятельные обновления, резервирование, мониторинг и восстановление |

Официальные материалы:
- Supabase: [регионы](https://supabase.com/docs/guides/platform/regions), [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security), [безопасность и GDPR](https://supabase.com/security).
- Firebase: [Security Rules](https://firebase.google.com/docs/rules/), [региональные endpoints](https://firebase.google.com/docs/firestore/regional-endpoints).
- Appwrite: [регионы](https://appwrite.io/docs/products/network/regions), [self-hosting](https://appwrite.io/docs/advanced/self-hosting).

## Безопасная модель данных

- Одна строка на пользователя; первичный ключ — auth user id.
- Доступ к строке разрешён только аутентифицированному владельцу через RLS.
- Клиент использует только publishable/anon key вместе с пользовательским access token. Service-role/admin ключи никогда не помещаются в браузер, репозиторий или localStorage.
- Запись выполняется через атомарную операцию compare-and-swap с ожидаемой ревизией. Конфликт возвращается пользователю; автоматическое «последняя запись победила» запрещено.
- Синхронизация запускается только после отдельного согласия. Локальный режим остаётся полноценным и доступным без аккаунта.
- Удаление облачной копии — отдельное действие; оно не удаляет локальную копию.
- Экспорт/импорт и локальное восстановление не зависят от backend.

## Почему облако пока не включено

Для реальной настройки нужен отдельный проект владельца, подтверждённый регион, настройки Auth, применение миграции SQL, проверка RLS двумя разными тестовыми пользователями и проверка удаления. Эти параметры нельзя выдумывать или безопасно подставить автоматически. До выполнения проверок синхронизация остаётся выключенной.

Перед переносом личных записей в облако владелец приложения должен отдельно оценить условия сервиса, сроки хранения, резервные копии, удаление, доступ сотрудников провайдера и применимые требования к данным о здоровье. Указание EU-региона не заменяет эту оценку.
